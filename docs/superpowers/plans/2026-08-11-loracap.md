# `loracap` 메서드 등록 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** LoRA의 학습 용량만 키운 `loracap` 방법을 등록해, 파라미터 용량 축의 단독 기여를 ablation으로 측정할 수 있게 한다.

**Architecture:** 코드 변경이 없다. `configs/methods/loracap.yaml` 한 장이 baseline의 학습 토글 다섯 개를 그대로 두고 `lora` 블록만 덮어쓴다. 기존 `all-mlp`/`all-proj`/`all-r32` arm이 이미 `lora` 오버라이드 경로가 동작함을 입증했으므로, 이 방법은 그 셋을 하나로 합쳐 baseline 위에 얹는 것이다.

**Tech Stack:** PyYAML, pytest (코드 변경 없음)

**근거 문서:** `docs/superpowers/specs/2026-08-10-training-method-comparison-design.md` §3.5

## Global Constraints

- 플랫폼은 Windows. 파이썬은 반드시 `.venv/Scripts/python.exe`를 쓴다. 전역 파이썬의 torch는 CPU 빌드라 사용 금지.
- 주석·로그·커밋 메시지는 한국어. 기존 코드 스타일(간결한 한국어 주석, 왜를 설명)을 따른다.
- 새 의존성을 추가하지 않는다.
- 단위 테스트는 GPU·모델 로딩 없이 도는 것만 작성한다. 스모크는 예외.
- 메서드 정의는 `configs/methods/<name>.yaml` 한 장 + `src/registry.py` 병합이 유일한 경로다. `src/registry.py`는 `name / description / extends / data / model / lora / train` 외의 최상위 키에 대해 예외를 던진다.
- `loracap`은 baseline 위에 **파라미터 용량 축 하나만** 바꾼다.
- `loracap`은 `DEFAULT_ARMS`에 넣지 않는다 — `--arms`로만 선택하는 opt-in이다.

## 왜 코드가 필요 없는가

`configs/methods/`에 이미 세 개의 LoRA 오버라이드 arm이 있다.

```yaml
all-r32:   lora: {r: 32, alpha: 64}
all-mlp:   lora: {target_modules: [q_proj, k_proj, v_proj, out_proj, fc1, fc2]}
all-proj:  lora: {train_projections: true}
```

셋 다 `all` 레시피 위에 얹혀 있어 다른 개선들과 기여도가 섞인다. `loracap`은 같은 세 가지
변경을 **baseline 위에** 한꺼번에 얹어, 비교표의 Δ가 파라미터 용량 축의 기여가 되게 한다.
`src/model.py`가 이 세 키를 이미 읽고 있으므로 새 코드는 없다.

베이스 `lora` 블록(`configs/lora_clip.yaml`)은 `r: 16`, `alpha: 32`,
`target_modules: [q_proj, k_proj, v_proj, out_proj]`, `train_projections: false`다.

---

## 이 계획에 `hires378`을 넣지 않는 이유

스펙 §3.4의 `hires384`는 지금 착수하지 않는다. 모델(`models/metaclip-2-worldwide-huge-378`,
7.1GB)은 내려받아 두었고 `image_size: 378`, patch 14, `projection_dim: 1024`로 확인됐다.
막는 것은 VRAM이다.

```
224 해상도: (224/14)² = 256 토큰,  batch 32 → peak 23GB (스펙 실측)
378 해상도: (378/14)² = 729 토큰 = 2.85배
              → batch 32 추정 65GB > 32GB
                batch 16 추정 33GB > 32GB
                batch  8 추정 16GB (들어감)
```

배치를 8로 줄이면 대조학습의 **네거티브 수가 32→8로 함께 줄어든다** — `grad_accum`은
네거티브를 늘려주지 못한다(네거티브는 물리 배치 안에서 나온다). 그러면 해상도 축과
네거티브 수 축이 동시에 바뀌어 `bigbatch`와 기여도가 섞이는데, 이는 `s16-384`를 배제했던
것과 같은 이유다.

`bigbatch`(GradCache)가 먼저 들어오면 물리 배치 8에서도 유효 네거티브 32를 유지할 수 있어
이 문제가 사라진다. 따라서 순서는 **`loracap` → `bigbatch` → `hires378`**이다.

> **이름 참고**: 스펙 §3의 표는 이 방법을 `hires384`로 적었으나 실제 모델 해상도는 378이다.
> 384는 배제된 `s16-384` 후보에서 온 숫자다. 착수 시 `hires378`로 등록하고 스펙 표기를
> 함께 고친다.

- [ ] **Step 1: 메서드 YAML 작성**

`configs/methods/loracap.yaml`:

```yaml
name: loracap
description: "LoRA 용량 확장 - rank 32, fc1/fc2 추가, projection 학습 (baseline + 파라미터 용량 축만 변경)"
extends: configs/lora_clip.yaml
data: {builder: shared, pairs: data/pairs.jsonl}
train:
  pk_views: 1
  locarno_aware: false
  mask_false_negatives: false
  augment: false
  img2img_weight: 0.0
lora:
  r: 32
  alpha: 64
  target_modules: ["q_proj", "k_proj", "v_proj", "out_proj", "fc1", "fc2"]
  train_projections: true
```

`train` 블록의 다섯 값은 `configs/methods/baseline.yaml`과 **정확히 같아야 한다.** 열어서
대조한 뒤 저장한다. `description`에 em 대시(`—`)를 쓰지 않는다 — cp949 콘솔에서 인코딩할 수
없어 러너/학습이 죽는다(이 저장소에서 두 번 발생했다). 아스키 하이픈을 쓴다.

- [ ] **Step 2: 실패하는 테스트 작성**

`tests/test_method_configs.py` 끝에 추가:

```python
def test_loracap은_baseline과_lora_블록만_다르다():
    """loracap이 바꾸는 축은 파라미터 용량 하나여야 Δ가 그 기여로 읽힌다."""
    c = registry.resolve("loracap")
    b = registry.resolve("baseline")
    five = ("pk_views", "locarno_aware", "mask_false_negatives", "augment", "img2img_weight")
    assert [c["train"][k] for k in five] == [b["train"][k] for k in five]
    assert c["model"] == b["model"], "loracap은 모델을 바꾸지 않는다 (해상도 축은 hires378의 몫)"


def test_loracap의_lora_블록이_베이스보다_크다():
    """세 가지가 모두 켜져야 '용량 확장'이다 - 하나라도 빠지면 다른 arm과 구분되지 않는다."""
    c = registry.resolve("loracap")["lora"]
    b = registry.resolve("baseline")["lora"]
    assert c["r"] > b["r"] and c["alpha"] > b["alpha"]
    assert set(c["target_modules"]) > set(b["target_modules"]), "fc1/fc2가 추가되지 않았다"
    assert c["train_projections"] is True and b["train_projections"] is False


def test_loracap은_손실과_배치_구성_축을_건드리지_않는다():
    """tic(손실 축)·hobit(배치 구성 축)과 겹치면 기여도가 섞인다."""
    c = registry.resolve("loracap")["train"]
    assert c.get("tic_weight", 0.0) == 0.0
    assert c.get("sampler", "random") != "hobit"
```

## 알려진 한계

- **세 가지를 한꺼번에 켠다.** rank·MLP·projection 중 무엇이 기여했는지는 이 arm으로 알 수
  없다. 기존 `all-mlp`/`all-proj`/`all-r32`가 그 분해를 담당하지만 그쪽은 `all` 레시피 위에
  있어 baseline 기준 분해는 아니다. 용량 축이 유의미하다고 나오면 그때 분해한다.
- **파라미터가 늘어 학습이 느려지고 VRAM을 더 쓴다.** 스펙의 batch 32 = peak 23GB는 rank 16
  기준이라 여유가 얼마나 남는지는 재지 않았다. 스모크에서 OOM이 나면 실전 실행 전에 재야 한다.
