# 학습 방법 비교: 현재까지의 실험 결과

- 작성 2026-08-12 · 대상 커밋 `ec6f9ff` (main)
- 비교 구조 설계: `docs/superpowers/specs/2026-08-10-training-method-comparison-design.md`
- 운영 문서: `ACCURACY.md`

## 요약

선정한 5개 방법 중 **4개가 구현·병합됐다**(`hobit`·`tic`·`loracap`·`bigbatch`). 남은
`hires378`은 `bigbatch`가 들어와야 성립하는 순서였고, 이제 조건이 갖춰졌다.

**검색 성능 비교(Δ R@K)는 아직 측정되지 않았다.** `outputs/methods/*/eval/`에 숫자가
있지만 갤러리 39개짜리 스모크 실행의 산출물이라 방법 간 비교에 쓸 수 없다(§4). 이
보고서가 담는 실험 결과는 **학습 비용(시간·VRAM·파라미터)과 단일 축 성립 여부**다.
둘 다 실전 비교를 돌리기 전에 반드시 알아야 하는 값이고, 실제로 이 측정이 두 번
설계를 바꿨다(`loracap`의 VRAM 스필, `bigbatch`의 숨은 정밀도 축).

---

## 1. 비교 구조

각 방법은 `baseline` 위에서 **정확히 한 축만** 바꾼다. 그래야 Δ를 그 축의 기여로 읽을
수 있다. `baseline`은 모든 개선이 꺼진 상태(`pk_views: 1`, 마스킹·증강·img2img 모두 off)다.

| arm | 바꾸는 축 | 구체적 변경 | 근거 |
|---|---|---|---|
| `baseline` | (기준점) | - | - |
| `hobit` | 배치 **구성** | 에폭마다 submodular greedy 재정렬 (`pool 4096`, `penalty 10.0`) | ① PK 샘플러의 원리적 대체 |
| `tic` | **손실** | 텍스트 모달 내부 대조항 (헤드명사 같고 코사인 < 0.92인 쌍만 0.75 위로) | ③ 같은 물품군의 다른 물품이 텍스트 공간에서 안 갈림 |
| `loracap` | 파라미터 **용량** | rank 16→32, fc1/fc2 추가, projection 학습 | ⑫ 표현력 상한 |
| `bigbatch` | 유효 **네거티브 수** | GradCache 청크 8개 → 유효 배치 32→256 | ⑩ 대조학습의 배치 크기 민감성 |
| `hires378` | 입력 **해상도** | 224 → 378 (미구현) | 도면 세부 선의 해상도 한계 |

축이 실제로 하나뿐인지는 테스트로 고정돼 있다. `registry.resolve()`가 만든 두 설정의
`train`/`lora`/`model` 블록을 통째로 비교해, 의도한 키 외에 다른 것이 섞이면 실패한다.
현재 테스트 168개 통과 / 13개 스킵.

## 2. 실측: 학습 비용

RTX 5090 (31.84 GiB), bf16, 224px, batch_size 32 고정.

| arm | 학습 파라미터 | 유효 네거티브 | peak VRAM | s/step | 표본당 | baseline 대비 시간 |
|---|---|---|---|---|---|---|
| `baseline` | 8,388,609 (0.45%) | 32 | 24.12 GiB | 0.31 | 9.6 ms | 1.00× |
| `hobit` | 8,388,609 | 32 | ≈ baseline | ≈ 0.31 | 9.6 ms | 1.00× + 에폭당 재정렬 |
| `tic` | 8,388,609 | 32 | ≈ baseline | ≈ 0.31 | 9.6 ms | ≈ 1.00× |
| `loracap` | 37,888,001 (2.00%) | 32 | 10.45 GiB ※ | 0.53 | 16.6 ms | **1.73×** |
| `bigbatch` | 8,388,609 | **256** | 24.10 GiB | 3.43 | 13.4 ms | **1.40×** |

※ `loracap`만 `gradient_checkpointing: true`라 peak가 오히려 낮다.

### 2.1 `loracap` - 용량을 키우면 VRAM이 먼저 터진다

파라미터를 4.5배로 늘리면 활성값도 같이 커진다. 체크포인팅을 끄면 **peak 32.03 GiB**로
31.84 GiB 카드를 넘어선다. 문제는 이때 크래시도 경고도 나지 않는다는 것이다 - Windows가
시스템 메모리로 스필하고 **0.28 → 4.05 s/step(약 14배)**이 된다. 13,285 step/epoch 기준
`--epochs 3`이 약 6시간에서 **약 45시간**이 된다.

체크포인팅을 켜면 peak 10.45 GiB / 0.53 s/step. 활성값을 저장하는 대신 backward에서
재계산하는 대가로 시간이 1.73배가 되지만, 45시간이 6시간이 된다.

`batch_size`를 줄여 VRAM을 맞추지 않은 이유: 배치를 줄이면 in-batch 네거티브 수까지 같이
줄어 Δ를 용량 축의 기여로 읽을 수 없게 된다. 축을 지키려고 시간을 낸 것이다.

### 2.2 `bigbatch` - VRAM을 안 늘리고 네거티브만 8배

대조학습의 네거티브는 물리 배치 안에서 나온다. `grad_accum`을 올려도 네거티브는 늘지
않는다(손실이 배치마다 따로 계산되므로). GradCache는 이 결합을 끊는다: 1패스는
`no_grad`로 청크별 임베딩만 모으고, 2패스는 청크별로 다시 순전파하며 1패스에서 얻은
임베딩 그래디언트를 주입한다. 활성값을 청크 하나 분량만 들면 되므로 메모리는 물리
배치에 비례하고 손실은 전체를 본다.

실측이 이를 확인한다: **peak_reserved가 baseline 24.12 GiB / bigbatch 24.10 GiB로 사실상
같은데 유효 네거티브는 32 → 256**이다.

비용은 전부 시간으로 나온다. 옵티마이저 스텝당 0.31 → 3.43초지만, 한 스텝이 처리하는
표본이 8배(32 → 256)라 **표본당으로는 1.40배**(9.6 → 13.4 ms)다. 순전파가 fwd+bwd의 약
1/3이라는 통념(+33%)과 맞는 값이다.

> 계획 단계에서 적어둔 "스텝당 약 2배" 기대치는 한 스텝이 처리하는 표본이 8배라는 점을
> 빼먹은 표현이었다. 실측으로 정정했다.

### 2.3 `hobit` - 비용이 학습이 아니라 재정렬에 있다

배치 구성이 "현재" 모델 기준이어야 hard negative가 의미를 갖는다. 그래서 에폭마다 학습
분할 전체를 1회 추론해 임베딩을 갱신한다. 전체 425,140장 기준 실측 **디코딩 98.6분 +
ViT-H forward 27.9분**. 디코딩이 비용의 78%라 학습 로더와 같은 `num_workers`로 병렬화한다.
줄이려면 `hobit_refresh_every`를 2 이상으로 둔다(N 에폭마다 1회).

## 3. 실측: 설계를 바꾼 두 발견

측정하지 않았으면 잘못된 결론을 냈을 두 지점을 기록해 둔다.

**(1) `tic`의 1차 설계는 측정으로 반증됐다.** 원래는 "제목이 다른 쌍을 밀어낸다"였는데,
실제 모델로 코사인 분포를 재보니 목표 쌍은 마진 아래에, 무관한 쌍은 위에 있었다. 항의
기여가 4e-6이었다 - 이름만 tic인 baseline이 될 뻔했다. 헤드명사 + 상한(0.92) 기준으로
재설계해 배치당 대상 쌍 3.20개를 확보했다.

**(2) `bigbatch`에 숨은 두 번째 축이 있었다.** 기존 경로는 손실을 `autocast` 안에서
계산하는데 GradCache 경로만 밖에서 계산했다. 모델이 임베딩을 fp32로 내놓기 때문에
밖에서는 로짓이 fp32, 안에서는 bf16이 된다 - 즉 `bigbatch`만 손실을 더 정밀하게 계산해
Δ가 "네거티브 8배 + 손실 정밀도" 두 축의 합이 될 뻔했다(그래디언트 차이 0.3~0.6%).
최종 리뷰에서 잡아 autocast로 감쌌고, 수정 후 손실이 4.5508 → 4.5507로 baseline과 같은
정밀도로 맞는 것을 GPU에서 확인했다.

## 4. 아직 측정되지 않은 것: 검색 성능

`outputs/methods/*/eval/`에 T2I R@K와 mAP가 있지만 **방법 비교에 쓸 수 없다.**

| arm | T2I R@1 | T2I R@10 | mAP | 학습 레코드 | 갤러리 |
|---|---|---|---|---|---|
| `base` (튜닝 전) | 0.3684 | 0.7895 | 0.4873 | - | 39 |
| `baseline` | 0.3421 | 0.7895 | 0.4906 | 361 | 39 |
| `hobit` | 0.3684 | 0.8158 | 0.4952 | 361 | 39 |
| `tic` | 0.3421 | 0.7895 | 0.4906 | 361 | 39 |
| `loracap` | 0.3684 | 0.8158 | 0.4925 | 361 | 39 |

못 쓰는 이유가 넷이다.

1. **갤러리 39개, 쿼리 38개.** 쿼리 1개가 R@1 0.026이다. 위 표에서 arm 사이의 모든 차이가
   쿼리 1~2개 분량이다. 실운용 갤러리는 472,615장이다.
2. **학습 레코드 361개, 1 에폭.** 배치 구성·네거티브 수·파라미터 용량 같은 축은 데이터가
   이 규모면 애초에 발현되지 않는다. `bigbatch`의 유효 배치 256은 전체 학습 집합이
   361개일 때 의미가 없다.
3. **`tic`의 평가값이 `baseline`과 소수점 끝까지 동일하다**(0.4906346792182706). 어댑터
   파일이 평가 산출물보다 나중에 쓰였다 - 평가가 옛 어댑터를 본 것이다.
4. **`outputs/methods/baseline`은 어댑터와 평가·인덱스가 서로 다른 학습을 가리킨다.**
   `bigbatch` 비용 측정이 어댑터를 덮어썼다.

즉 **현재 저장소에는 유효한 검색 성능 비교가 하나도 없다.** 위 표는 파이프라인이
끝까지 돈다는 증거이지 성능 증거가 아니다.

## 5. 실전 비교를 돌리는 법

`--force`가 필수다. 어댑터·평가·인덱스 세 스킵 검사를 모두 우회한다. 붙이지 않으면
위 스모크 산출물을 학습 완료로 보고 건너뛰어 **조용히 틀린 표**가 나온다.

```powershell
# 10만 부분집합 (권장 시작점)
python scripts\run_ablation.py --arms baseline hobit tic loracap bigbatch `
  --data data\subset_100k.jsonl --epochs 3 --force
```

### 시간 추정

`data/subset_100k.jsonl` = 101,444장 / 13,002 디자인. `eval_ratio 0.1` 적용 시 학습 분할
약 91,300장 → batch 32에서 약 2,853 step/epoch. 아래는 §2의 실측 s/step에서 유도한 값이다.

| arm | step/epoch | 3 에폭 학습 | 비고 |
|---|---|---|---|
| `baseline` | 2,853 | 약 44분 | |
| `tic` | 2,853 | 약 44분 | |
| `bigbatch` | 357 | 약 61분 | 스텝 수는 1/8, 표본당 1.40배 |
| `loracap` | 2,853 | 약 76분 | 체크포인팅 1.73배 |
| `hobit` | 2,853 | 약 83분 | + 에폭당 재정렬 약 13분 |
| **학습 소계** | | **약 5.1시간** | |
| 인덱스 6개 | | 약 1.3시간 | 10만장 인코딩 × 6 |
| **합계** | | **약 6~8시간** | |

전체 `data/pairs.jsonl`(472,615장)로 돌리면 약 4.7배 - **30시간 이상**이고 `hobit`의
재정렬 비용은 그보다 더 가파르게 는다. 설계 단계에서 "부분집합으로 비교하고 승자만
풀규모"로 정한 이유가 이것이다.

## 6. Δ를 읽을 때의 주의

방법별로 Δ가 무엇을 뜻하지 **않는지**를 미리 못 박아 둔다.

**`tic`** - 헤드명사 축이 범용 통 하나에 쏠려 있다. 배치당 대상 쌍의 **47.5%가 헤드명사
`device` 하나**에서, 58.7%가 범용 헤드 6종에서 나온다. 레코드의 20.2%는 전치사·보어
때문에 헤드가 물품에서 밀려나 있다(`... for a vehicle` → `vehicle`). **`tic`의 Δ를 목표
물품군(box·carrier·panel 계열)에 대한 증거로 읽으면 안 된다** - 그 쌍들은 배치당 0.02쌍
수준이라 Δ에 사실상 기여하지 않는다.

**`hobit`** - 배치가 GPU 임베딩에 의존하므로 같은 seed라도 배치 순서가 달라질 수 있다.
다른 arm과 달리 완전 재현되지 않으며, **Δ의 실행 간 분산이 다른 arm보다 크다.** 작은
Δ를 유의하다고 읽기 전에 재실행이 필요하다.

**`bigbatch`** - **학습 손실을 baseline과 직접 비교하면 안 된다.** InfoNCE는 후보 수의
로그에 비례해 커지므로(ln 256 = 5.55 vs ln 32 = 3.47) 같은 품질에서도 bigbatch 쪽이 크게
나온다. 실측 첫 스텝 4.55(bigbatch) vs 2.27(baseline)은 성능 차이가 아니다. 또 Δ는 "같은
시간에 더 나은 결과"가 아니라 **"같은 스텝 수에 더 많은 네거티브"**로 읽어야 한다 -
표본당 1.40배의 시간을 이미 쓰고 있다.

**`loracap`** - 시간 1.73배는 용량 자체의 비용이 아니라 VRAM을 맞추려 켠 체크포인팅의
비용이다. 더 큰 카드에서는 이 비용이 사라진다.

## 7. 남은 작업

- **`hires378`** - 5개 중 마지막. 378 해상도는 토큰이 2.85배라 물리 배치 8이 한계인데,
  `bigbatch`가 들어왔으므로 물리 8에서도 유효 네거티브 32를 유지할 수 있어 해상도 축만
  바뀌는 비교가 성립한다. 모델(`models/metaclip-2-worldwide-huge-378`)은 확보돼 있다.
  스펙 §3.4의 `hires384` 표기를 `hires378`로 고치는 작업이 함께 들어간다.
- **실전 비교 1회** (§5). 이것이 없으면 이 프로젝트의 원래 질문에 답이 없다.
- **테스트 공백** - GradCache 등가성 테스트는 CPU 장난감 인코더를 쓰므로 `train.py`의
  실제 2패스 경로를 타지 않는다. §3(2)의 autocast 결함이 정확히 이 공백에서 나온 종류다.
  그룹 스텝을 인코딩 콜러블을 받는 헬퍼로 빼면 CPU 토이 모델로 실경로를 태울 수 있다.
- **`outputs/methods/` 정리** - 스모크 산출물이 남아 있다. `--force` 없이 돌리면 이것들이
  Δ의 분모가 된다.
