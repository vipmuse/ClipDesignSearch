## 요약

**loracap이 I2I 승자**(mAP +3.3pp), **hires378이 유일하게 I2I와 T2I를 모두 올린 방법**이다
(I2I mAP +3.1pp, T2I mAP +0.6pp). 나머지 셋은 이기지 못했다: hobit은 I2I를 올리는 대신
T2I를 크게 내렸고, tic은 사실상 무승부, bigbatch는 전 지표 하락(단 §3.4의 스텝 수 교란
때문에 "네거티브가 나쁘다"로 읽으면 안 된다).

LoRA 튜닝 자체의 효과가 어떤 방법 간 차이보다 크다: base → baseline이 I2I mAP
0.367 → 0.537(+17.0pp), T2I mAP 0.163 → 0.251(+8.8pp)이다. 방법 간 Δ는 그 위의 ±3pp 싸움이다.

Δ는 baseline 대비. **볼드**는 열별 최고.

| loracap | **0.8944 (+1.6pp)** | **0.9534 (+0.6pp)** | **0.5704 (+3.3pp)** | 0.3351 (−0.3pp) | 0.5472 (−2.0pp) | 0.2527 (+0.2pp) |
| bigbatch | 0.8668 (−1.2pp) | 0.9380 (−0.9pp) | 0.5128 (−2.4pp) | 0.3297 (−0.8pp) | 0.5624 (−0.5pp) | 0.2471 (−0.4pp) |

**유의성 잣대**: T2I는 쿼리 1,113개라 쿼리 1개 = 0.09pp. ±0.3pp 이내는 쿼리 3개 차이로
소음일 수 있다. I2I는 쿼리 9,931개라 쿼리 1개 = 0.01pp로 훨씬 촘촘하다. 위 표에서
loracap·hires378의 I2I +3pp대는 쿼리 300개 이상이 갈린 것으로 소음이 아니다.
hobit의 T2I −2.9pp도 쿼리 32개로 실재한다. loracap의 T2I −0.3pp는 소음 범위다.

## 3. 방법별 해석

### 3.1 loracap — I2I 승자, 비용도 가장 건전

용량 4.5배(8.4M → 37.9M)가 I2I 전 지표를 올렸고 T2I는 중립이다(mAP +0.2pp는 소음 범위).
체크포인팅 덕에 peak 10.43 GiB로 **표에서 VRAM이 가장 낮고**, 남는 21 GiB는 나중에 다른
축(해상도·배치)과 결합할 여지다. 시간 1.73배는 체크포인팅 비용이며 용량 자체의 비용이
아니다.

### 3.2 hires378 — 유일한 양쪽 개선, 특히 T2I

해상도 224 → 378이 I2I mAP +3.1pp에 더해 **T2I를 올린 유일한 방법**이다(mAP +0.6pp,
R@10 +2.5pp). 도면의 얇은 선이 정보의 전부라는 이 방법의 가설과 부합한다. baseline과
같은 8,577 스텝, 같은 유효 네거티브 32(물리 8 × 청크 4)로 돌았으므로 축이 깨끗하다 —
bigbatch를 먼저 넣어 GradCache를 확보한 순서가 여기서 값을 했다.

비용은 표에서 가장 크다(246분, baseline의 4.6배). 유효 배치 유지에 GradCache 비용
(표본당 1.4배)이 이미 포함된 값이다.

### 3.3 hobit — I2I와 T2I의 트레이드오프

I2I mAP +2.3pp를 얻는 대신 T2I R@1 −2.9pp를 냈다. 시각적으로 비슷한 하드 네거티브를
배치에 몰아넣는 방식이 이미지 변별은 돕지만 텍스트 정렬을 해쳤을 가능성이 있다 — 다만
이는 사후 가설이고, hobit은 배치가 GPU 임베딩에 의존해 **완전 재현되지 않는 arm**이므로
(같은 seed라도 배치 순서가 달라질 수 있음) 이 Δ를 확정으로 읽기 전에 재실행이 필요하다.

### 3.4 bigbatch — 전 지표 하락, 단 스텝 수 교란이 있다

유효 네거티브 32 → 256이 이 설정에서는 도움이 되지 않았다(I2I mAP −2.4pp). **그러나 이
Δ를 "네거티브 8배의 순수 기여"로 읽으면 안 된다.** 에폭 예산이 고정이라 옵티마이저
스텝이 8,577 → 1,071로 1/8이 됐고, 학습률은 관행(배치에 비례한 스케일링)과 달리
baseline과 동일하게 뒀다. 즉 이 결과는 "같은 에폭·같은 LR에서 갱신 횟수를 1/8로 줄이고
네거티브를 8배로 늘리면 손해"라는 뜻이다. 네거티브 축 자체를 판정하려면 (a) LR을
√8~8배로 올리거나 (b) 스텝 수를 맞춘(에폭 8배) 재실행이 필요하다. 위안이 되는 실측:
우려했던 loss=nan은 8,577 스텝 통틀어 0건, peak 24.04 GiB로 VRAM 스토리는 확정됐다.

### 3.5 tic — 예고된 무승부

스펙 §7.4의 경고("대상 쌍의 47.5%가 범용 헤드 device 하나에 쏠림")가 그대로 실현됐다.
TIC 항 자체는 정상 작동했다 — 초반 배치당 위반 1~8쌍이 스텝 2,000 무렵 0으로 수렴하고
이후 유지됐다(로그의 위반/대상 카운트). 즉 항은 일을 다 했는데 그 일이 검색 지표를
움직이지 못한 것이다. 밀어낸 쌍이 대부분 범용 헤드 조합이라 평가 쿼리와 무관했다는
해석과 부합한다. 헤드 선택 규칙을 바꾸지 않는 한(불용 목록·전치사 절단·로카르노 기반)
이 방법은 기각이 합리적이다.

## 4. 권고

1. **풀규모(472,615장) 승자 실행은 loracap과 hires378 두 개로.** loracap은 I2I 최우선일 때,
   hires378은 T2I(텍스트 검색)까지 고려할 때의 선택이다. 둘은 직교 축(용량 vs 해상도)이라
   결과를 보고 결합 arm(loracap+hires378)을 시도할 여지도 있다 — loracap의 peak 10.4 GiB와
   hires378의 17.6 GiB를 합쳐도 카드에 들어갈 가능성이 높으나 결합 시 실측이 먼저다.
2. **hobit은 보류.** I2I 이득이 loracap보다 작고 T2I 손실이 크다. 재현성 문제로 재실행
   검증 비용도 있다.
3. **tic은 기각.** 헤드 선택 규칙 재설계 없이는 재시도 무의미.
4. **bigbatch는 축 판정 미완.** 기각이 아니라 미판정이다. LR 스케일링 또는 스텝 맞춤
   재실행 없이는 결론을 낼 수 없고, hires378의 기반 기술(GradCache)로서의 역할은 이미
   증명됐다.

## 5. 재현

```powershell
# 데이터: 6개 arm YAML의 data.pairs = data/subset_100k.jsonl (커밋 240f210)
python scripts\run_ablation.py --arms baseline hobit tic loracap bigbatch hires378 --epochs 3 --no-index --force
python scripts\run_ablation.py --report-only   # 표 재생성
```

- arm별 산출물: `outputs/methods/<arm>/` (final/ 어댑터, eval/final.json, train.log)
- 결과 표 원본: `outputs/methods/summary.md`
- 학습 중 로그의 `[epoch N]` R@K는 **배치 내 평가라 arm 간 비교 불가**
  (hires378은 배치 8이라 R@10이 자명하게 1.0). arm 비교는 반드시 eval/final.json의
  전체 갤러리 수치로 한다.
- hobit은 완전 재현되지 않는다(배치가 GPU 임베딩 의존). 나머지 arm은 seed 42 고정.
